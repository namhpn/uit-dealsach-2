## Requirements

### 1. Preserve API-backed AlertPage behavior

- Keep `/alerts` driven by existing APIs:
  - `fetchPriceAlerts()`
  - `fetchAlertPreferences()`
  - `updateAlertPreferences()`
  - `updatePriceAlertTarget()`
  - `pausePriceAlert()`
  - `reactivatePriceAlert()`
  - `renewPriceAlert()`
  - `restartPriceAlertTracking()`
  - `disablePriceAlert()`
- Do not introduce mock alert data.
- Do not add alert API fields.
- Do not add, remove, or rename alert lifecycle endpoints.
- Preserve loading, error, empty, unauthenticated, populated, active, paused, auto-paused, expired, and disabled states.

### 2. AlertPage purpose and information hierarchy

- Treat AlertPage as a buyer-facing price-watch dashboard, not a technical alert audit page.
- Optimize the page for active purchase decisions first and lifecycle traceability second.
- Show buyer-friendly data only in the main scan path.
- Keep secondary/debug-like details visually subordinate.
- Do not expose raw backend implementation details as primary UI.

### 3. AlertPage header

- Replace the current plain heading/email header with a stronger DealSach Neubrutalist header:
  - stamped `Cảnh báo giá` title;
  - uppercase, extra-bold Be Vietnam Pro treatment;
  - black border;
  - hard 8px black shadow;
  - sharp corners;
  - optional subtle `-1deg` rotation;
  - short explanatory text block with a strong emerald left rule.
- Header copy must explain the buyer value:
  - saving watched books;
  - tracking target prices;
  - receiving email when prices become suitable.
- Add compact stat/status chips near the header:
  - active count;
  - paused/attention count where available;
  - account email state.
- The logged-in email may remain visible but must not be the primary visual element.

### 4. Account email preference panel

- Preserve the existing account-level alert email preference behavior.
- Keep one global email preference control only.
- Restyle the preference panel into a compact control strip:
  - white or bone-white surface;
  - 2px black border;
  - 4px hard shadow;
  - title;
  - concise description;
  - one tactile toggle button.
- The panel must not visually dominate active alerts.
- Do not add per-alert email toggles.
- If account email is disabled, cards may show a compact warning chip such as `Email đang tắt`.

### 5. Buyer-friendly status grouping

- Do not map every raw status to an equal section.
- Group alerts as:
  - `Đang theo dõi`: only `Active`;
  - `Cần chú ý`: `Paused`, `Auto-paused`, and `Expired`;
  - `Đã tắt`: `Disabled`.
- Keep exact status visible as a badge on each card.
- `Expired` must remain actionable with `Gia hạn`.
- `Disabled` alerts must remain visible by default but compact and visually quiet.

### 6. Section styling

- `Đang theo dõi`:
  - highest visual priority;
  - 20px uppercase section title;
  - hard black divider;
  - emerald count badge;
  - strongest card treatment.
- `Cần chú ý`:
  - medium priority;
  - include paused, auto-paused, and expired alerts;
  - explain that these alerts need review or renewal.
- `Đã tắt`:
  - lower priority;
  - compact history-style rows or compact cards;
  - muted/dashed/outline-variant treatment;
  - no primary price-watch emphasis.

### 7. Alert card shell

- Replace the current dense metric-card look with a buyer-facing alert card layout.
- Use a local `AlertCard` implementation inside `AlertsPage.tsx`.
- Desktop card layout should clearly separate:
  - cover/status column;
  - book and price-watch content;
  - action rail or action cluster.
- Mobile layout may stack, but must preserve scan order:
  - book identity;
  - status;
  - key price-watch numbers;
  - actions.
- Card shell:
  - white active background;
  - 2px black border;
  - hard black shadow;
  - no border radius;
  - tactile hover/focus/pressed behavior where appropriate.

### 8. Cover and status treatment

- Use existing `CoverImage` behavior for cover rendering and fallback.
- Add a stable cover frame with book-like proportions.
- Attach the primary alert status badge to the cover area or top of the card.
- Status badge labels:
  - `Đang theo dõi`
  - `Tạm dừng`
  - `Tự tạm dừng`
  - `Hết hạn`
  - `Đã tắt`
- Badge styling:
  - uppercase;
  - 9–10px;
  - extra-bold;
  - black border;
  - sharp corners.
- Use emerald for active, bone-white for paused, warning treatment for auto-paused/expired, and muted/danger treatment for disabled.

### 9. Book metadata hierarchy

Each active/attention card must show:

- alert type chip:
  - `Giá mục tiêu`
  - `Giá thấp mới`
- book title:
  - link to `/book/{bookId}` when a book exists;
  - clamp long titles;
- author;
- publisher where available;
- category;
- created date or expiry date in a compact secondary position.

Do not show book descriptions.

### 10. Price hierarchy for target-price alerts

For `alert_type === "target_price"`:

- Main price block 1: `Giá mục tiêu`
  - emerald background;
  - white text;
  - large price.
- Main price block 2: `Giá hiện tại`
  - bone-white or white background;
  - black text;
  - show current lowest eligible price when available;
  - show `Chưa có giá đủ điều kiện` when unavailable.
- Main price block 3: buyer condition:
  - if current price is above target, show remaining amount as `Còn {amount}`;
  - if current price is at or below target, show `Đã chạm mục tiêu`;
  - if current price is unavailable, show `Đang chờ giá`.
- Do not claim an email was sent unless recent events explicitly support that.
- Do not show notification count as a primary metric.

### 11. Price hierarchy for new-lowest alerts

For `alert_type === "new_lowest_price"`:

- Main price block 1: `Mốc theo dõi`
  - show `baseline_price` when available;
  - show `Chờ giá đủ điều kiện` when `baseline_pending` is true or baseline is unavailable.
- Main price block 2: `Giá hiện tại`
  - show current lowest eligible price when available;
  - show `Chưa có giá đủ điều kiện` when unavailable.
- Main price block 3: buyer condition:
  - if current price is lower than baseline, show `Giảm {amount}`;
  - if baseline is pending, show `Đang chờ mốc`;
  - otherwise show `Chưa thấp hơn mốc`.
- Do not invent retailer names, seller names, or “tại Tiki” messaging unless existing DTO fields already provide that data.

### 12. Secondary alert details

- Move these out of the main scan path:
  - comparison price;
  - last notified price;
  - notification count;
  - recent events.
- Show secondary details only in a compact details strip or secondary block.
- Translate recent event keys into Vietnamese labels.
- Show only the latest 1–3 recent events.
- Do not display raw event keys like `target_price_updated`, `email_sent`, or `tracking_restarted`.

### 13. Alert actions

- Preserve existing lifecycle actions.
- Use buyer-facing labels:
  - `Sửa` for editing target price;
  - `Tạm dừng`;
  - `Tiếp tục`;
  - `Gia hạn`;
  - `Theo dõi lại`;
  - `Tắt`.
- Do not use `Xóa`.
- Do not implement permanent delete.
- Destructive `Tắt` action must remain visually distinct but not use a confirmation modal.
- Disable or prevent duplicate action clicks while an action is in flight if this can be implemented locally without broad refactor.
- Keep success/error feedback in Vietnamese.

### 14. Target-price editing interaction

- Do not show the target-price edit form by default on every card.
- Put target editing behind `Sửa`.
- When expanded:
  - show a compact inline form;
  - keep current target value prefilled;
  - input accepts only positive integer VND;
  - label: `Giá mục tiêu VND`;
  - save button: `Lưu giá`;
  - cancel/close affordance: `Hủy` or repeated `Sửa` toggle.
- Preserve existing validation behavior:
  - target price must be a positive integer VND.
- Do not support switching alert type in this ticket.

### 15. Disabled/history treatment

- Disabled alerts must remain visible by default.
- Render disabled alerts as compact history-style rows or compact muted cards.
- Disabled rows must show:
  - book title;
  - author/category if space allows;
  - alert type;
  - final status `Đã tắt`;
  - latest translated recent event or updated date if available.
- Disabled rows must not show large primary price blocks.
- Disabled rows must show `Chỉ xem lịch sử` or equivalent non-actionable treatment.
- Do not add a separate history API.

### 16. Empty, loading, error, and unauthenticated AlertPage states

- Loading, error, and empty states must remain Vietnamese-first and match the Neubrutalist style.
- Empty state must include a CTA to `/search`, such as `Tìm sách để theo dõi`.
- Unauthenticated users must not see the full management dashboard.
- Unauthenticated users should see a strong page-level login prompt card with:
  - `Cảnh báo giá`;
  - buyer-focused description;
  - one clear login CTA that opens the shared auth dialog.
- Keep existing auth dialog open behavior.

### 17. Shared login prompt card pop-up

Refine the existing email-code auth dialog in `frontend/src/app/auth/AuthContext.tsx`.

- Keep the existing email-code authentication flow.
- Do not add phone login.
- Do not add Google/Facebook/social login buttons.
- Do not add fake authentication options.
- Do not change backend auth APIs.
- Do not change session persistence semantics.
- Preserve:
  - email entry step;
  - verification-code step;
  - resend cooldown;
  - error handling;
  - close behavior;
  - `openAuthDialog()` and `closeAuthDialog()` public behavior unless a tiny optional local extension is required and remains backward compatible.

### 18. Login prompt visual structure

- Convert the dialog from a narrow single-column utility modal into a wider split card:
  - desktop max width around `760px–820px`;
  - left panel for email-code sign-in;
  - right panel for DealSach value messaging;
  - collapse to one column on mobile.
- Keep DealSach visual identity:
  - sharp corners;
  - 2px black border;
  - hard black shadow;
  - flat colors;
  - Be Vietnam Pro;
  - no gradients;
  - no rounded Tiki-style card treatment.
- Overlay remains a darkened page.
- Close button:
  - square;
  - black border;
  - white or bone-white background;
  - tactile hard shadow;
  - positioned clearly at top-right.

### 19. Login prompt left panel content

- Replace the system-like visible title with friendly buyer-facing copy:
  - headline: `Xin chào,`
  - subheadline: `Đăng nhập để lưu sách và theo dõi giá`
  - helper copy: `DealSach gửi mã xác minh qua email. Không cần mật khẩu.`
- Email step:
  - label: `Email nhận mã xác minh`;
  - input has 3px black border or visually stronger border than normal body inputs;
  - primary button text: `Tiếp tục`.
- Code step:
  - show a clear message that code was sent to the entered email;
  - label: `Nhập mã 6 số`;
  - primary button text: `Xác minh & đăng nhập`;
  - secondary resend control remains available with cooldown;
  - provide an affordance to go back/change email if practical without broad refactor.
- Error/success messages must remain Vietnamese.

### 20. Login prompt right value panel

- Add a DealSach-specific value panel rather than copying Tiki’s blue promotional panel.
- Panel content should emphasize:
  - `Theo dõi giá sách thông minh`;
  - wishlist;

  - new-lowest-price alerts;
  - transparent reference-price behavior;
  - external-seller handoff.
- Suggested benefit rows:

- Use DealSach colors:
  - emerald;

  - bone-white;
  - white;
  - black outlines.
- Decorative elements may be CSS-only blocks/icons already available through existing dependencies.
