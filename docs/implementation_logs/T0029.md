## Requirements

### 1. Admin information architecture cleanup

- Keep `/admin` as the Admin landing page.
- `/admin` must show the dashboard experience and use the page title `Dashboard quản trị`.
- Remove the visible `/admin/menu` Admin menu route.
- Clean up `AdminPage.tsx` so it no longer exposes a visible duplicate Admin menu page.
- Preserve `AdminGate` behavior for all Admin pages.
- Remove `/admin/reports` if it is not needed as a separate route.
- If `/admin/reports` is removed:
  - remove its route entry;
  - remove its import;
  - remove or delete `AdminReportsPage.tsx` if it becomes unused.
- Do not leave dead visible navigation pointing to `/admin/menu` or `/admin/reports`.

### 2. Admin navigation pattern

- Admin pages should use a compact, consistent top navigation action set:
  - `Dashboard quản trị`
  - `Sách`
  - `Ưu đãi`
  - `Người dùng`
  - `Cảnh báo`
  - `Quản trị logs`
- `/admin` must not show a back link.
- Other Admin pages may show a back/navigation action to `/admin`, but do not label it `Về Admin`.
- Use `Dashboard quản trị` or `Về Dashboard quản trị` instead of `Về Admin`.
- Avoid duplicating a full Admin menu card grid on every page.

### 3. Terminology and Vietnamese copy

Use the agreed terms consistently:

- `Dashboard quản trị`
- `Báo cáo 7 ngày gần đây`
- `Quản trị logs`
- `Lượt chuyển hướng Affiliate`
- `Lỗi liên kết mua`
- `Lượt mở liên kết email`
- `Quản trị viên`
- `Người dùng`
- `Email Preference`
- `Số cảnh báo giá`
- `Số email đã gửi`
- `Logs`
- `Tắt cảnh báo`

Do not use `Admin` in page titles except where referring to the role if unavoidable.

### 4. Dashboard cleanup

- Keep dashboard metric cards, but group them into clearer sections instead of one flat undifferentiated grid.
- Keep existing dashboard data semantics.
- Keep lightweight bar/chart-style report blocks; do not add a new charting dependency.
- Remove this text from the dashboard:
  - `Múi giờ: Asia/Ho_Chi_Minh. Không dùng khoảng ngày tùy chỉnh.`
- Do not expose “custom date range is unavailable” copy.
- Translate raw alert status labels in dashboard tables using the same Vietnamese status map as Admin alert pages.
- Avoid showing the same metric twice unless one is a summary and the other explains it with meaningful detail.

### 5. AdminUsersPage cleanup

- Keep user email visible in the table.
- Show role labels as:
  - `Quản trị viên`
  - `Người dùng`
- Keep email alert preference visible.
- Rename the email preference column to `Email Preference`.
- Keep values as `Bật` / `Tắt`.
- Rename the alert count column to `Số cảnh báo giá`.
- Replace slash-only alert count text such as `1/3` with readable text such as:
  - `1 đang theo dõi / 3 tổng`
- Keep deactivate/reactivate behavior unchanged.
- Do not add confirmation dialogs in this ticket.

### 6. AdminAlertsPage cleanup

- Keep user email visible.
- Rename the notification-count column from `Email` to `Số email đã gửi`.
- Keep one latest event only.
- Rename the latest-event column to `Logs`.
- Keep alert status labels in Vietnamese:
  - `Đang theo dõi`
  - `Tạm dừng`
  - `Tự tạm dừng`
  - `Hết hạn`
  - `Đã tắt`
- Change the disable action label from `Tắt` to `Tắt cảnh báo`.
- Keep the existing Admin disable action behavior unchanged.
- Do not add alert detail pages or expandable event history in this ticket.

### 7. AdminAuditPage cleanup

- Keep the audit page available.
- Keep raw `action_type` and `entity_type` values as-is; do not translate them in this ticket.
- Remove these visible columns from the default audit table:
  - `Tóm tắt`
  - `Trước`
  - `Sau`
- Keep the default audit table focused on readable columns:
  - `Thời gian`
  - `Admin`
  - `Hành động`
  - `Đối tượng`
- Do not change audit API behavior or backend audit data.
- Do not add a new audit detail page in this ticket.

### 8. AdminCatalogPage cleanup

- Continue using generic `AdminCatalogPage` temporarily for:
  - books
  - retailers
  - merchants
  - offers
- Remove generic category code from `AdminCatalogPage`; categories are handled by `AdminCategoriesPage`.
- Keep `AdminCategoriesPage` as the dedicated categories page.
- Replace always-visible create forms above generic catalog tables with a clear create button that opens a dialog/panel.
- The create trigger must use full text labels:
  - `Tạo sách`
  - `Tạo nền tảng bán lẻ`
  - `Tạo nhà bán`
  - `Tạo ưu đãi`
- Do not use icon-only `+` create buttons.
- Keep existing create/update/archive/restore API calls and semantics.
- Use existing shared styles; do not add a modal/dialog dependency.

### 9. AdminBooksPage behavior inside AdminCatalogPage

- Replace `ID danh mục` with a category select for book creation, using existing available category data.
- Keep inline metadata editing for now, but compact the presentation.
- Change the featured action label:
  - when not featured: `Đánh dấu nổi bật`
  - when featured: `Bỏ nổi bật`
- Keep book create/update/archive/restore behavior unchanged.

### 10. AdminRetailersPage and AdminMerchantsPage behavior inside AdminCatalogPage

- Keep `Slug` visible but visually secondary.
- Show approved retailer domains as chips instead of comma-only text where practical.
- Replace `ID nền tảng` with a retailer/platform select for merchant creation.
- Keep retailer and merchant create/update/archive/restore behavior unchanged.

### 11. AdminOffersPage behavior inside AdminCatalogPage

- Replace raw ID fields in offer creation with selects where practical:
  - book select
  - retailer/platform select
  - merchant select
- Translate known eligibility review reasons into Vietnamese.
- Keep raw fallback text only for unknown reason codes.
- Keep offer create/update/status behavior unchanged.
- Do not change offer eligibility rules.

### 12. Admin offer observation detail cleanup

- Keep `/admin/offers/:id` behavior unchanged.
- Keep the current file name `AdminBookDetailPage.tsx` for this ticket; do not rename it.
- Improve visible labels so the page reads as an offer-observation page.
- Split raw observation status triplets into labeled Vietnamese chips, for example:
  - `Sách: Hoạt động`
  - `Ưu đãi: Có thể mua`
  - `Liên kết: Hợp lệ`
- Translate known raw statuses where practical.
- Keep observation create/history behavior unchanged.

### 13. Admin style consistency

- Keep admin-specific `AdminHeader`; do not switch Admin pages to public `StampHeading`.
- Standardize section cards and tables below the header.
- Reduce table border density:
  - keep Neubrutalist shell border and hard shadow;
  - avoid heavy repeated `border2` on every cell when row dividers are enough.
- Use status chips only for actual status fields.
- Do not turn every count/metadata value into a chip.
- Standardize success messages with one shared/admin notice pattern where practical.
- Keep loading and error behavior using existing shared states.
- Keep Admin minimum width support at 768px.

### 14. Documentation

- Add `docs/implementation_logs/T0029.md`.
- Add a focused T0029 section to `docs/Manual_Verification_Guide.md`.
- Update `docs/Repo_Current_State.md`.
- Update `docs/Known_Issues_And_Followups.md` only if a new out-of-scope issue is discovered.
- Do not fix KI-0009, KI-0014, or KI-0015 in this ticket.
